# Product Roadmap V1

## 路线图定位

这份 V1 路线图回答的不是“还能继续加什么功能”，而是：

> **这个项目应该先长成什么样的产品，哪些能力要先做，哪些能力暂时不要做。**

当前项目最合适的目标，不是做成 `Notebook Navigator` 那样的综合导航平台，而是继续把 `Folder Card Explorer` 推进成一个：

> **以响应式卡片墙为核心的笔记浏览、筛选、搜索与整理工作台。**

它的中心应该始终是 **card-wall-first workbench**，而不是文件浏览器替代品。

## 产品愿景

V1 版本要解决的核心问题是：

- 用户能在一个稳定驻留的侧边栏工作台里，用卡片墙快速浏览一个范围内的笔记。
- 这个范围不仅可以来自文件夹，也可以来自 `All Notes`、标签筛选和搜索结果。
- 用户可以在卡片墙里完成高频整理动作，而不必频繁切回文件管理器。
- 用户查看和编辑笔记时，仍然主要沿用 Obsidian 原生工作流。

V1 的目标体验应当是：

1. **卡片墙负责浏览与整理。**
2. **主显示区负责深度阅读与编辑。**
3. **快速预览是增强能力，不是主编辑形态。**

## 当前状态（V1 起点）

项目当前已经具备继续向 V1 推进的稳定骨架：

- 文件管理器点击联动右侧视图已稳定。
- `All Notes`、面板内文件夹选择、排序、标签筛选、置顶、单卡片复制/移动等交互已接入主流程。
- `FolderCardView` 已经承担运行时协调职责，`pipeline.ts` 已成为可见卡片投影挂点。
- 视图层已经具备虚拟滚动、视口驱动 hydration、generation 防陈旧结果、debounced vault observers 等性能约束。

这意味着项目并不是“从零规划”，而是已经处于：

> **功能骨架已稳定，正在决定应该朝“更完整的卡片工作台”演进到什么程度。**

## V1 产品边界

### 要做成什么

V1 的产品形态定义为：

- 一个右侧 leaf 中长期驻留的响应式卡片墙。
- 支持按文件夹、`All Notes`、标签和搜索结果切换与筛选范围。
- 支持多选、批量操作、文档合并等整理工作流。
- 支持“点击卡片 -> 主显示区打开笔记”的主模式。
- 支持卡片墙上的快速预览能力，作为次级增强模式。

### 明确不做什么

V1 暂不把目标定义为：

- 替代 Obsidian 原生文件管理器
- 引入第二导航 pane、属性树、日历、profile、快捷入口系统
- 做成多视图协调的综合导航平台
- 在每张卡片里直接嵌入完整编辑器

这条边界很重要。只要越过它，项目复杂度就会迅速接近 `docs/explore/notebook-navigator.md` 中总结的重型架构。

## V1 设计原则

V1 继续沿用当前项目已经验证过的四个原则：

1. **性能优先**：不牺牲虚拟化、视口驱动 hydration、增量刷新与 generation 模型。
2. **本地优先**：搜索、索引、缓存和批量操作都保持本地运行。
3. **原生感优先**：笔记打开、叶子管理、菜单与交互尽量沿用 Obsidian 原生模式。
4. **边界清晰**：`FolderCardView` 仍是协调层，Svelte 组件不演化成业务状态源。

## V1 分阶段路线

### Phase 1：把卡片墙工作台做完整

这是 V1 最优先的一段，也是产品形态真正成型的阶段。

目标：

- 将当前单列卡片流推进为 **响应式卡片墙**。
- 把文件夹、`All Notes`、标签筛选统一成更自然的范围切换体验。
- 保持现有“点击卡片 -> 主显示区打开笔记”为默认主模式。
- 补齐 `includeSubfolders` 等已经进入设置层、但面板入口未完全闭环的体验缺口。

重点产出：

- 响应式多列布局
- 视图内范围切换与筛选入口统一
- 更清晰的 Toolbar 信息层次
- 不破坏当前性能模型的 wall virtualization 方案

完成标志：

- 卡片墙从“单列浏览器”升级成“可长期使用的视觉工作台”
- 用户在常见浏览路径上不必依赖文件管理器树作为唯一入口

### Phase 2：补齐批量整理能力

这是把卡片墙从浏览器升级成整理台的关键阶段。

目标：

- 引入基于路径的多选状态
- 支持范围选中、全选/取消选择、选中计数
- 补齐批量移动、批量删除、批量合并的用户可见工作流

对应任务基础：

- `docs/dev-feature/task-18-batch-select-framework.md`
- `docs/dev-feature/task-19-batch-move-delete.md`
- `docs/dev-feature/task-20-batch-merge.md`

重点产出：

- 多选交互框架
- 批量动作入口与确认链路
- 合并顺序、分隔符、预览与错误反馈

完成标志：

- 用户可以把卡片墙真正当作一块“整理工作台”使用
- 常见批量整理动作不需要回退到外部插件或手动操作

### Phase 3：把搜索做成真正能力

这是一条独立的重要能力线，也是 V1 中最可能引入新数据边界的一段。

目标：

- 把搜索从当前占位能力推进成真正可用的 scoped search
- 搜索与现有 tag filter、pin reorder、默认排序规则正确组合
- 在索引未就绪时可降级，而不是直接失效

对应任务基础：

- `docs/dev-feature/task-21-plan-e-spike.md`
- `docs/dev-feature/task-22-search-service-contract.md`
- `docs/dev-feature/task-23-index-store.md`
- `docs/dev-feature/task-24-minisearch-manager.md`
- `docs/dev-feature/task-25-index-build-incremental.md`
- `docs/dev-feature/task-26-index-health-rebuild.md`
- `docs/dev-feature/task-27-search-ui.md`

路线原则：

- 先验证 `IndexedDB + MiniSearch` 的可接受性，再决定是否正式引入持久化索引。
- 搜索关键词维持视图级临时状态，不进入持久化设置。
- 搜索先作为 pipeline 的一段，而不是另起平行可见性系统。

重点产出：

- `SearchService` 契约
- `IndexStore` 与增量更新策略
- 搜索 UI、降级提示、排序与高亮基础能力
- 索引损坏恢复和重建入口

完成标志：

- 搜索体验从“简单过滤”提升为“可依赖的主要入口之一”
- 大量笔记场景下仍能保持合理响应

### Phase 4：预览增强、视觉收尾与可访问性

这是 V1 的收束阶段，目标不是继续扩边界，而是把核心体验打磨成熟。

目标：

- 提供卡片墙上的快速预览增强能力
- 完成视觉一致化、间距与层级整理
- 补齐 i18n、键盘导航和 ARIA 基线

对应任务基础：

- `docs/dev-feature/task-28-visual-consistency.md`
- `docs/dev-feature/task-29-card-appearance.md`
- `docs/dev-feature/task-30-i18n-a11y.md`

这里的一个重要原则是：

> 快速预览可以进入 V1，但“把卡片墙变成多编辑器宿主”不属于 V1。

更适合的方向是：

- 主模式仍然是点击卡片在主显示区打开笔记
- 增强模式是轻量浮窗预览、临时查看、必要时转交给原生 leaf 编辑

完成标志：

- 视觉风格更统一
- 基础可访问性具备
- 快速预览不会破坏卡片墙主工作流

## 推荐交付顺序

建议按下列顺序推进，而不是按“哪个功能最有吸引力”随机插入：

1. 响应式卡片墙与范围/筛选闭环
2. 多选与批量操作
3. 搜索服务与索引能力
4. 快速预览增强
5. 视觉一致化与 i18n / a11y 收尾

原因很简单：

- 没有稳定的卡片墙形态，多选和搜索都很难有清晰归宿。
- 没有多选框架，批量操作只是工具函数，不是完整工作流。
- 没有真正搜索服务，插件很难从“浏览辅助”升级为“主要入口”。
- 视觉和 a11y 应在主交互稳定后做收束，而不是提前打磨。

## 主要收益

如果按这个路线推进，V1 的收益主要体现在四个方面：

1. **产品辨识度增强**：形成明显区别于 Navigator 类产品的 card-wall-first 形态。
2. **日常使用频率更高**：用户可以把它当作固定工作台，而不是偶尔打开的视图。
3. **整理能力明显增强**：从“看笔记”升级到“整理笔记”。
4. **搜索价值真正建立**：从依赖文件夹树进入，转向依赖卡片墙与搜索共同驱动。

## 主要风险

### 1. 响应式卡片墙的虚拟化复杂度

当前实现本质上还是单列垂直流。升级为多列响应式布局后，位置计算、滚动锚定和高度波动都会更复杂。

### 2. `FolderCardView.ts` 持续膨胀

当前决策已经明确接受它作为协调核心，但 V1 期间应警惕继续把所有状态推进、动作路由和刷新编排都塞进同一个文件。

### 3. 搜索体验预期高于实际实现

一旦用户看到搜索框，预期往往就是“快、准、能解释结果”。如果没有索引、降级、排序和健康恢复机制，体验会明显不稳。

### 4. 快速预览与编辑边界失控

预览是合理增强；但如果把“快速预览”扩展成“卡片墙内长期编辑宿主”，会立刻引入更高的焦点管理和生命周期复杂度。

## 不做清单（V1）

以下方向暂时不进入 V1：

- 多 pane 导航器布局
- property tree / calendar / vault profile
- 以插件接管整个文件浏览体验为目标
- 把卡片墙做成完整编辑器容器
- 在没有验证规模压力前，过早复制重型 provider / service / cache 体系

这些并不是永远不做，而是它们会把项目从当前路线拉向另一类产品。

## V1 完成标准

满足以下条件时，可以认为 V1 产品形态基本成立：

- 卡片墙已从单列流升级为稳定可用的响应式工作台
- 文件夹 / `All Notes` / 标签 / 搜索形成统一范围与过滤体验
- 批量选择、批量移动/删除/合并已具备完整用户闭环
- 搜索已成为真实可依赖入口，而非占位过滤
- 默认主工作流仍保持 Obsidian 原生感
- 视觉一致化、基础 i18n 和 a11y 已补齐到可发布水平

## 一句话判断

V1 不应该追求“做得像 Notebook Navigator 一样全”，而应该追求：

> **把当前项目推进成一个真正好用、可持续扩展、以卡片墙为核心的笔记工作台。**
